## Product promise and present evidence

CONSTRUCTOR AI aims to turn a bounded user request into software that a person
can inspect, test, approve, export and recover. Its intended advantage is the
combination of explicit requirements, evidence-bound changes, independently
checked outcomes and human authority. This is a product hypothesis, not a
claim of superiority or a claim that competitors lack these features.

The source already provides a local Template Studio with Task Manager, Business
CRM and Dashboard templates, portable source exports, local browser storage,
automated tests and a documented Chromium acceptance run. The limited
task-manager VELION adapter, quarantine, Docker-based synthetic QA and
verification-only local review approval are separately implemented. These are
not a general-purpose prompt-to-production application factory.

A historical [real-model experiment](VERIFIED_REAL_LLM_MICROCOMPONENT_20261031.md)
generated one invoice calculation module with a third-party local model and
passed ten pre-authored checks on a bounded task. That record also documents
uncovered edge cases. It is evidence of that one microcomponent, not evidence
of a production CRM, a continuously operating agent, proprietary model weights
or broad model reliability.

As of the 2026-11-05 review, no real customer acceptance, payment, verified
full-app model-generated release, signed Owner key enrollment, production
AI Passport, persistent cross-process replay protection or deployed
multi-tenant platform is established by this blueprint.

## Canonical architecture

The Architect defines mission and authority. HANTER is the AI Command Center
and delegates to the appropriate independent domain orchestrator. Authorized
professional Nano Core Agents work inside bounded runtime domains. VELION is
the model intelligence and routing layer; MAX is a mode, not a renamed product.
ORION may provide bounded advisory intelligence when explicitly enabled.

Intake produces a versioned IntentLock with goal, allowed workspace and tools,
time and resource caps, acceptance criteria and a data classification. AI
Passport identity and Enterprise Skills do not grant authority. Guardian Core
and Approval Gateway evaluate the requested action; the runtime is isolated
from unrelated projects, secrets, external accounts and the separate CRYPTO
IMPERIAL Ecosystem Boundary. ProofGraph and Audit Ledger retain evidence and
uncertainty; Owner Kill Switch revokes the ability to continue. A local HMAC
permit is not a deployed implementation of these components.

## User experience

1. Describe the application or change and inspect a concise requirements draft.
2. Confirm the workspace, data classification, permitted tools, acceptance
   criteria, provider/model and spend/time limits.
3. Review a plan and a proposed source diff before authorized execution.
4. Build and test inside an isolated ephemeral runtime. Display failed checks,
   retries and a stop control; never hide uncertainty behind a green badge.
5. Examine results, independent acceptance, proof links and the exact changed
   files. Export a local review copy or deploy only under the appropriate
   separately verified approval.
6. Preserve a recoverable baseline and verify rollback. Keep user data private
   and enable export without forcing a single model or provider.

## Delivery sequence and acceptance gates

| Increment | Deliverable | Evidence required before promotion |
| --- | --- | --- |
| 0. Scope integrity | Local mission-goal, route and model bound permit v2 | Negative substitution, expiry and replay tests; exact commit CI; no claim of owner identity |
| 1. One real application | One independently specified Task Manager built from a real prompt/model output in an isolated workspace | Raw model response identity, immutable source hashes, separately authored hidden tests, browser behavior, reproducible CI and honest failures |

| 3. Domain extension | CRM and Dashboard generated with bounded contracts | Separate tests and usable demos for each; safe persistence and restore |
| 4. Governed team runtime | HANTER delegation to a federated domain, scoped NCA and independent QA | Cryptographic passport, revocation, durable replay defense, kill-switch and actual runtime receipts |
| 5. Customer pilot | One narrowly scoped agreed customer outcome | Real product fit, authorized access, data protection, tested handover, defined support and actual acceptance |
| 6. Competitive comparison | Cursor/Hermes comparison on the same tasks and budgets | Versioned benchmark, comparable environments and models, independent scoring and published failures |
| 7. Production | Approved managed operation | Threat review, recovery drills, cost evidence, documented reliability and explicit authorization |

## Competitive benchmark

Prepare at least 20 licensed or original representative tasks, including a
fresh application, an existing-repository change, a bug, data migration,
accessibility, a bounded security case and recovery. Keep acceptance tests
independent of the builder; maintain held-out tests. Pin source revision,
product/model versions, data, hardware, network, permissions, time and total
budget. Record success and failure, unauthorized side effects, intervention
count, elapsed time, actual measured costs and reproducibility. Run enough
repetitions to explain variation and report sample size. A single demo,
simulated model, fixed template or historical run cannot prove superiority.

## Commercial first step

Offer a synthetic-data demonstration of the existing local single-user CRM,
including source, backup/restore and documented tests. A paid delivery is
conditional on licensing, fit, buyer requirements, security review, actual
costs and a separate agreement. Do not represent this demonstrator as
multi-user, cloud-hosted, autonomous AI, a deployed integration or a
production-ready enterprise system. See
[OFFLINE_CLIENT_CRM_RELEASE.md](OFFLINE_CLIENT_CRM_RELEASE.md).

## Operating constraints

No hidden paid inference, paid hosting, mass agent creation, private customer
data upload, token transaction or deployment is implied by this document.
Provider budgets and zero-cost eligibility require current evidence. Record
DESIGNED, IMPLEMENTED, TESTED, DEPLOYED and VERIFIED separately for every
material feature. Preserve third-party licenses and contribution history.
